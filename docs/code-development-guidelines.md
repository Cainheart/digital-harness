# 代码开发准则

> 适用范围：`backend/`、`frontend/` 以及 `docs/task/` 中所有任务的代码开发、代码修改和代码评审。
> 当前生效版本：V1

## 1. 目的

本准则用于保证代码的职责、边界和变更原因能够被后续开发者快速理解，并让代码实现与 PRD、需求矩阵、概要设计和 Task 验收标准保持可追踪。

## 2. TypeScript 优先的实现语言规范

本项目主要使用 TypeScript 开发，TypeScript 仍然是默认首选语言。它适合当前 AI 项目的控制面、领域模型、共享协议、类型约束、工具编排和前后端协作；项目级目标仍是让 TypeScript 占生产源代码的主要比例，但比例目标不能凌驾于实际场景、性能、平台能力和可维护性之上。

如果某个特定场景使用其他语言或技术更合适，可以根据实际需求进行选择。例如：高并发或系统级后端服务可以评估 Go，数据处理、模型工具链或科学计算可以评估 Python，前端样式应使用 CSS 或项目约定的样式方案，浏览器运行时代码或轻量脚本可以使用 JavaScript，Node.js 适合 JavaScript/TypeScript 的服务运行时和工具生态。语言选择必须由职责、依赖、性能、部署方式、安全边界、团队维护成本和与现有系统的集成难度共同决定，不能只因为个人熟悉度或短期编码方便而变更。

使用非 TypeScript 语言或技术时，必须在对应的详细设计、Task 或 Review 记录中说明：选择原因、负责范围、输入输出契约、进程/部署边界、错误处理方式、与 TypeScript 模块的集成方式以及后续维护策略。不得因为引入其他语言而复制一套已有业务规则，也不得让非 TypeScript 实现绕过统一的权限、审计、数据校验和错误边界。

当前 V1 的后端控制面、流程编排、执行面和桌面 sidecar 默认采用 Node.js/TypeScript 方案，包括 Fastify、TypeBox、LangGraph.js、TypeScript Worker、Drizzle ORM 和 TypeScript Model Adapter。`frontend/`、Electron、共享协议、工程工具和测试代码原则上保持 TypeScript 优先；如果实际需求表明 Python、Go、CSS、JavaScript 或 Node.js 更适合，则应按本节标准进行技术评估和记录，而不是机械地强制所有代码使用 TypeScript。

## 3. 代码排版、可读性和文件命名规范

### 3.1 代码排版与可读性

开发代码时，正确性和可读性同等重要。代码必须让其他开发者能够在 Review 时快速看清控制流、数据流、异常边界和副作用，禁止为了减少行数而牺牲结构清晰度。

必须遵守以下要求：

- 默认一行只表达一个主要逻辑动作；不得把多个语句、多个赋值、条件判断、事务操作或返回逻辑用分号挤在同一行。
- `if`、`else`、`for`、`while`、`switch`、`try/catch` 等控制结构必须使用清晰的多行块；条件较长时拆成有意义的布尔变量或独立校验函数。
- 不得把复杂的箭头函数、对象构造、数据库事务、Promise 链、错误处理或策略判断压缩成一行。函数体超过一条主要逻辑时，应展开为多行并保持合理缩进。
- 避免深层嵌套三元表达式、超长布尔表达式和连续方法链；应通过命名变量、早返回、辅助函数或分段处理表达业务意图。
- 单行长度以不影响阅读为原则，通常控制在 120 个字符以内；如果一行包含多个概念，即使没有超过 120 个字符，也应主动换行。
- 代码格式化工具只能统一缩进和基础排版，不能替代可读性判断；格式化后仍需人工检查是否出现“整段逻辑挤成一行”的结果。
- 新增代码必须保持与所在模块一致的缩进、括号、换行和空行风格；如果原文件已经难以 Review，应在本次修改范围内逐步拆分，不得继续复制低可读性写法。

推荐写法：

```typescript
const isExpired = leaseExpiresAt <= now;
const isOutsideProject = action.projectId !== grant.projectId;

if (isExpired || isOutsideProject) {
  return reject("执行授权已过期或超出项目范围");
}
```

禁止写成：

```typescript
if (leaseExpiresAt <= now || action.projectId !== grant.projectId) return reject("执行授权已过期或超出项目范围");
```

简单的单一 guard clause 可以保持简短，但只要条件、表达式或副作用开始变长，就必须展开为多行。代码不得以“能运行”作为压缩成单行的理由。

### 3.2 文件命名规范

代码文件名必须根据文件承担的业务职责、领域对象或提供的服务命名，不能根据开发任务编号命名。`task1.ts`、`task2.ts`、`task3.ts`、`task4.ts` 等名称无法表达代码做什么，也不允许作为生产代码、测试代码或共享模块的默认命名方式。

必须遵守以下要求：

- TypeScript/JavaScript 文件默认使用小写 `kebab-case`，名称应由业务概念和职责组成，例如 `organization-policy-service.ts`、`structured-message-repository.ts`、`execution-grant-policy.ts`。
- 测试文件同样按被测业务能力命名，例如 `organization-policy.test.ts`、`structured-message.test.ts`、`schema-integrity.test.ts`，不得使用 `task3.test.ts` 作为唯一语义。
- 文件名优先使用稳定的业务名词或服务名，不使用临时实现名、个人姓名、日期、Issue 编号或 Task 编号作为主体名称。
- `index.ts`、`main.ts`、框架规定的入口文件以及明确的配置文件可以使用约定名称，但必须保证目录本身能够表达其模块职责。
- 新建文件前必须先检索现有目录，确认职责是否已有对应模块；如果已有模块职责过大，应优先拆分或重命名，而不是再创建一个模糊的 `utils.ts`、`helpers.ts` 或 `taskN.ts`。
- 重命名文件时必须同步更新 import、测试、脚本、文档和构建配置；重命名不能只改文件名而留下失效引用或语义不一致的导出名。
- Task 编号只用于任务文档、分支名、提交信息和验收证据，不用于替代代码文件的业务命名。

Code Review 必须特别检查：文件名是否能让不了解当前 Task 的开发者理解其职责，代码是否存在可通过拆分函数、变量和条件来显著提升可读性的单行或超长实现。

### 3.3 复用现有实现，避免重复逻辑

新增代码前必须先确认项目中是否已经存在可以复用的函数、方法、全局变量、常量、枚举、类型、配置、工具模块或其他实现。不得因为当前文件中暂时没有直接看到对应代码，就立即复制一份相同或近似的逻辑。

必须遵守以下要求：

- 新增函数或方法前，先使用代码搜索检查现有模块、领域服务、Repository、Policy、工具函数和共享类型，确认没有已经实现相同职责的代码。
- 新增全局变量、常量、枚举、状态映射、默认配置或宏定义前，先检查是否已有统一定义；相同业务含义只能保留一个权威来源，禁止在多个文件中各自维护一份字面量或列表。
- 需要使用其他文件已经提供的函数时，优先通过明确的 import 复用，不得把函数实现复制到当前文件后再稍作改名。
- 如果现有实现只差少量能力，应优先扩展现有实现、增加参数或抽取共享函数，而不是创建一个职责重叠的新函数。
- 如果现有实现职责过大、命名不准确或边界不适合复用，应先重构为清晰的共享模块，再由调用方统一引用；不得以复制代码作为临时解决方案。
- 新增实现确有必要时，必须在代码 Review 或变更说明中写明：已检查过哪些现有实现、为什么不能直接复用、为什么新实现的职责边界不会与现有代码重叠。
- 复制代码、复制常量列表、复制策略规则、复制错误处理或复制数据转换逻辑都视为潜在重复实现，必须在 Review 中解释其必要性。
- 新增宏定义或编译期常量时，必须先检查构建配置、共享配置模块和现有常量注册位置；宏或全局配置不得散落在业务文件中。

推荐的开发顺序是：

```text
搜索现有实现
    -> 判断是否可以直接复用
    -> 判断是否应扩展或重构现有实现
    -> 只有确认不存在合适实现时才新增代码
    -> 在 Review 记录新增原因和职责边界
```

代码 Review 必须检查新增函数、变量、常量、配置和跨文件引用是否经过现有实现检索；发现两个实现承担相同业务职责时，应优先合并为单一实现或要求提交者说明保留两份的理由。

### 3.4 代码健壮性、边界和兜底要求

确认代码质量时，无论是业务代码、基础设施代码、工具代码、脚本还是测试辅助代码，都必须明确可能出问题的边界在哪里。代码不能只验证正常输入和主流程成功，还必须主动讨论异常输入、外部依赖失败、资源限制、状态冲突和部分完成等情况，并为这些情况制定可执行的兜底措施。

必须遵守以下要求：

- 开发前先列出函数、模块或接口的输入边界、输出边界、状态边界、权限边界、时间边界、资源边界和外部依赖边界。
- 对空值、错误类型、非法枚举、超长输入、重复请求、过期数据、跨项目/跨角色对象、路径穿越、命令注入、网络失败、文件不存在、数据库冲突、超时、取消和部分成功等场景进行分析。
- 每个函数都必须保护其可能失败的地方：校验输入、检查前置条件、处理异常、保持事务一致性、避免资源泄漏，并返回稳定、可理解、可恢复的错误结果。
- 不能用宽泛的 `catch`、静默忽略、返回 `undefined`、默认放行或吞掉错误日志来伪装“有兜底”；兜底措施必须说明失败原因、影响范围、数据是否保留以及下一步动作。
- 对可重试操作必须明确幂等键、重试次数、退避方式和重复执行的影响；对不可重试操作必须阻止重复提交并保留冲突证据。
- 对外部服务、模型、浏览器、容器、文件系统和数据库等依赖，必须考虑不可用、响应异常、版本不兼容、连接中断和返回数据不符合契约的情况。
- 对并发修改和状态竞争，必须使用事务、版本号、租约、条件更新或其他明确机制，不能依赖“通常不会同时发生”的假设。
- 兜底行为不得绕过权限、审批、只读、审计、数据隔离或安全门禁；失败时宁可阻断并保留数据，也不能使用未审计的隐式降级。
- 边界分析应转化为自动化测试，至少覆盖成功路径、失败路径、极值、重复调用、并发/重试、依赖不可用和恢复路径；发现新的边界缺陷时必须增加回归测试。

代码 Review 必须能够回答以下问题：边界在哪里、最坏情况是什么、函数如何保护、失败后数据是否一致、调用方收到什么错误、是否可以安全重试、是否留下了可追踪证据。如果这些问题无法回答，代码不能视为完成。

### 3.5 清理不再需要的代码、文件和目录

随着任务逐步完成，必须主动清理已经不再使用或后续也不再需要的函数、方法、变量、常量、业务逻辑、兼容分支、代码文件和目录，避免工程不断堆积无效实现。代码存在于仓库中不等于它仍然有价值；无法被调用、无法被验证、职责已经被替代或已经超出当前设计范围的代码，应在确认安全后删除。

必须遵守以下要求：

- 删除函数、变量、常量或业务逻辑前，先搜索静态引用、动态 import、注册表、依赖注入、路由、事件订阅、任务配置、脚本入口、构建配置和运行时约定，确认没有隐藏调用方。
- 删除文件或目录前，必须检查 import/export、测试、CLI 脚本、package 配置、构建配置、迁移入口、部署配置、文档链接和资源引用，不能只根据文件名或当前没有明显调用就直接删除。
- 如果代码是公共导出、插件入口、框架自动发现文件、配置约定文件或供外部消费者使用的接口，必须先确认兼容性影响和替代路径。
- 被新实现完全替代的旧实现、临时兼容分支、重复工具函数、废弃常量和不可达逻辑应优先清理；如果暂时不能删除，必须记录保留原因、使用方、删除条件和预计清理时机。
- 删除业务逻辑时，必须确认不会破坏状态迁移、权限边界、审计、历史数据读取、恢复流程和向后兼容；数据库历史数据和不可变事件不能因为清理代码而丢失。
- 删除后必须同步清理失效 import、导出、类型、测试、mock、fixture、脚本和文档，并运行类型检查、构建和相关测试确认没有残留引用。
- 不得为了让测试通过而保留明显无用的生产代码，也不得用注释掉的大段旧代码代替删除；历史版本应交给 Git 记录。
- 删除操作必须在 Review 中说明删除对象、确认过的引用范围、替代实现、删除原因和验证结果；涉及公共 API、迁移或目录结构时，应额外说明兼容性风险。

推荐的清理顺序是：

```text
搜索引用和入口
    -> 判断是否仍被运行时、配置或外部消费者使用
    -> 确认替代实现和兼容性影响
    -> 删除代码/文件/目录
    -> 清理 import、测试、脚本和文档
    -> 执行 typecheck、build 和相关测试
    -> 在 Review 记录删除范围与验证结果
```

Code Review 必须关注“新增了什么”以及“什么已经可以删除”。如果一个函数、变量、业务逻辑、文件或目录已经没有明确消费者，也没有保留它的兼容性或历史原因，应要求清理或记录清晰的保留理由。

## 4. 必须遵守的注释规则

### 4.1 新建或重写代码

新建或重写代码时，必须对对应的函数、方法、类、接口、类型和常量定义添加简洁明了的注释说明。

注释至少说明以下信息中的必要部分：

- 代码负责什么职责；
- 输入、输出或关键约束是什么；
- 为什么存在特殊的安全、持久化、生命周期或兼容性处理。

推荐使用语言原生的文档注释形式：

```typescript
/** 检查数据库版本，拒绝不兼容版本的可写启动。 */
export function checkSchema(...): SchemaCheckResult {
  ...
}
```

```typescript
// 从控制面读取最新 readiness，页面不直接访问 Docker 或文件系统。
export async function fetchReadiness(): Promise<ReadinessView> {
  ...
}
```

常量也必须说明其业务含义、取值边界或被哪些策略消费。例如 Schema revision、默认本机地址、超时时间、状态映射表等不能只留下没有解释的字面量。

### 4.2 修复 Bug 或处理其他问题

后续如果因为 Bug、需求变更、兼容性问题、安全问题、性能问题或运行环境问题修改代码，必须在实际修改位置附近添加“修改说明”备注。每一处问题修复或问题处理都必须同时写明实际修改日期和修改原因，不能只在提交信息、Issue 或任务总结中补充，避免代码脱离上下文后无法追溯。

备注必须使用具体日期，日期格式统一为 `YYYY-MM-DD`，不得写“今天”“最近”或其他不明确的时间表达；同时必须解释为什么需要修改，不要只重复代码做了什么。如果同一处代码再次因为新的问题被修改，应更新日期和原因，保留仍然有效的历史背景。推荐格式：

```typescript
// 修改日期：2026-08-16
// 修改原因：Docker Desktop 在 macOS 上可能不把 CLI 放入 PATH，
// 因此保留应用安装目录回退路径，避免 readiness 错误判定 Engine 不可用。
const dockerCliPath = resolveDockerCliPathWithFallback();
```

```typescript
// 修改日期：2026-08-16
// 修改原因：后端 blocked 时必须保持启动按钮禁用，避免前端绕过 StartupGate 发起真实执行。
const blocked = ...;
```

如果修改涉及明确的 PRD、需求矩阵、验收标准或缺陷编号，应在备注中同时写出对应编号；如果没有编号，至少写清楚触发条件和要保护的行为。上面的 `2026-08-16` 仅用于展示格式，实际代码备注必须替换为该次真实修改发生的日期。

### 4.3 注释质量要求

- 注释要短、准确、与代码保持同步。
- 不为显而易见的语法重复写无价值注释。
- 不把实现细节写成与实际行为不一致的承诺。
- 不在注释中写入 API Key、Cookie、Token、个人隐私或其他敏感信息。
- 代码重构后必须同步更新原注释；失效注释应删除。
- 关键安全边界、持久化边界、进程边界和人工审批边界必须优先保留注释。

## 5. 对各 Task 的执行要求

`docs/task/task1.md` 至 `docs/task/task11.md` 的代码开发都必须遵循本准则：

1. 开发前先确认修改对应的 Task、PRD 条款、需求矩阵需求和验收标准。
2. 新建或重写函数、方法、类、接口、类型和常量时，先写清职责注释，再提交实现。
3. 开发代码时必须遵守本文件第 3.1 节的排版和可读性要求；不得把复杂逻辑、多个语句或控制流压缩成单行。
4. 新建或重命名代码文件时必须遵守本文件第 3.2 节的业务命名要求；禁止使用 `task1.ts`、`task2.ts`、`task3.ts` 等 Task 编号作为代码文件名。
5. 新增函数、全局变量、常量、宏定义或跨文件函数引用前，必须先搜索现有实现，优先复用、扩展或重构，避免重复逻辑。
6. 开发和 Review 时必须遵守本文件第 3.4 节，明确输入、状态、权限、资源和外部依赖边界，并为可能失败的路径设计可验证的兜底措施。
7. 代码逐步完成后，必须检查并清理不再使用的函数、变量、业务逻辑、文件和目录；删除前确认静态/动态引用、入口、配置、脚本、测试和文档依赖，删除后完成构建与测试验证。
8. 修复问题时，在实际修改位置附近添加包含实际修改日期（`YYYY-MM-DD`）和明确修改原因的“修改说明”备注，并在任务验收证据中记录触发条件和验证结果。
9. 注释变更不得替代自动化测试；行为变化仍然必须补充或更新测试。
10. 代码评审时检查“新增代码有职责注释”“问题修复有包含修改日期与修改原因的备注”“代码排版可读”“文件名符合业务职责”“新增实现经过复用性检查”“边界和兜底措施明确”“无用代码已清理或有保留理由”七项。
11. 开始开发一个 Task 前，必须基于最新的 `master` 创建该 Task 的独立分支，统一命名为 `dev/task-N`，例如 Task 1 使用 `dev/task-1`；禁止直接在 `master` 上开发 Task。
12. 该 Task 的代码、测试、文档修改和完成提交都必须发生在对应的 `dev/task-N` 分支上，并将分支推送到远程仓库供验收和 Review。
13. 只有当该分支的 Task 验收通过且 Review 成功后，才允许将其合并到 `master`；验收或 Review 未通过时不得合并，修复必须继续提交到同一个 `dev/task-N` 分支。
14. 合并到 `master` 后，必须在 Task 交付证据中记录分支名、完成提交哈希、Review 结果和合并提交哈希；`master` 只接受已验收、已 Review 的 Task 合并。

标准分支流程如下，`N` 替换为当前 Task 编号：

```bash
git switch master
git pull --ff-only origin master
git switch -c dev/task-N

# 在 dev/task-N 上开发、测试并提交
git add <task-files>
git commit -m "feat(task-N): complete task implementation"
git push -u origin dev/task-N

# 验收和 Review 成功后，才允许合并到 master
git switch master
git pull --ff-only origin master
git merge --no-ff dev/task-N
git push origin master
```

Task 1 的既有实现已按本准则补充基础注释。后续 DEV-02～DEV-11 的实现、重构和问题修复均以本文件为强制开发约束。

## 6. Code Review 代码审查要求

代码评审不是只检查“能否编译”或“主流程是否成功”，必须验证实现是否同时满足产品契约、需求边界、任务验收和设计约束。Task 评审应至少覆盖以下内容：

1. 追踪性：逐项对照 PRD、需求矩阵、Task 验收标准和概要设计；在 Review 记录或验收证据中写明对应编号、实现位置、测试证据和未覆盖项。发现需求、设计与代码冲突时，先记录冲突和影响，再决定修复或升级确认，不得用默认行为掩盖冲突。
2. 数据和接口：检查领域对象、API 输入、数据库字段、外键、唯一约束、索引、迁移和回滚/只读行为是否一致；确认新增字段在创建、读取、更新、幂等重试和历史数据路径上都被正确处理。
3. 业务边界：核对角色、责任领域、对象动作、Boss/员工边界、任务负责人、消息发送/接收方、审批流转和响应对象引用；越权、缺字段、状态不允许或对象不属于当前项目/任务时，应在写入业务事实前拒绝。
4. 安全边界：检查默认拒绝、Grant 的项目/任务/Attempt/角色/版本/工具/工作区/期限/trace 绑定，工具参数、路径模式、命令白名单和控制字符处理；伪造身份、过期授权、跨项目输入、扩大的工具/命令集合以及外部输入不能扩大权限。凭据、Token、Cookie、提示词和敏感原文不得进入日志、事件摘要或错误载荷。
5. 版本和审计：检查策略版本、任务版本、Attempt 快照、不可变历史、幂等键、expectedVersion、领域事件和安全审计是否保持一致；重复请求不得重复派发、重复确认或重复追加事件，策略变更不得回写历史授权。
6. 测试完整性：至少包含主流程、拒绝路径、空值/错误类型/边界长度、过期时间、跨项目/跨角色、路径穿越、命令注入、并发/幂等重试、迁移结构损坏和恢复/只读行为。测试不能只覆盖 HTTP 200 或单一 happy path；修复缺陷时必须新增能复现该缺陷的回归测试。
7. 交付记录：确认测试命令和结果可复现，代码注释与实际行为一致，Review findings 已关闭或明确保留风险，Task 分支、提交哈希、验收证据和合并状态已记录。

Review 输出至少使用以下字段：严重级别（P0/P1/P2/P3）、文件和行号、触发输入或复现步骤、实际结果、预期结果、对 PRD/需求/验收/设计的影响、修复提交或不修复理由、回归测试和剩余风险。建议按以下清单逐项勾选：

- [ ] PRD、需求矩阵、Task 验收标准和概要设计逐项核对，并记录追踪关系。
- [ ] API、领域模型、持久化字段/约束/索引、事务和迁移契约一致。
- [ ] 角色、对象、任务负责人、Boss 边界、工具、路径、命令和 Grant 默认拒绝且不能被输入扩权。
- [ ] 版本快照、历史不可变、幂等、状态机和领域/安全审计行为正确。
- [ ] 已补充拒绝、边界、注入、过期、跨范围、并发/幂等和迁移损坏测试。
- [ ] 每个 finding 都有严重级别、定位、复现、处理结果和剩余风险。
- [ ] 代码没有把复杂控制流、多个语句、事务或错误处理压缩成单行；长条件已拆分为可理解的变量或辅助函数。
- [ ] 文件名按业务职责和提供的服务命名，使用约定的 `kebab-case`；没有新增 `task1.ts`、`task2.ts`、`task3.ts` 或其他 Task 编号代码文件。
- [ ] 新增函数、全局变量、常量、宏定义和跨文件函数引用前已检索现有实现；没有复制已有逻辑或重复维护同一业务常量。
- [ ] 如果新增实现无法复用现有代码，Review 记录已说明检索范围、不能复用的原因和新实现的职责边界。
- [ ] 已明确代码边界、最坏情况、错误处理、兜底策略、可重试性、并发行为和外部依赖失败处理。
- [ ] 每个关键函数对可能出错的输入、状态、权限、资源和依赖进行了保护，失败时不会静默放行或吞掉错误。
- [ ] 技术选型与实际场景匹配；如果使用非 TypeScript 语言或技术，已记录选择原因、接口契约、集成边界和维护策略。
- [ ] 已检查并清理不再使用的函数、变量、业务逻辑、文件和目录；删除范围、替代实现、引用检查和验证结果已记录。
- [ ] 对暂时不能删除的遗留代码，已记录保留原因、实际使用方、删除条件和预计清理时机。
- [ ] 验收证据已更新，Task 分支未在验收和 Review 成功前合并到 `master`。

## 7. 提交前检查清单

- [ ] 新增或重写代码默认使用 TypeScript；非 TypeScript 实现有明确的必要性说明、边界和后续策略。
- [ ] TypeScript 优先原则没有因个人熟悉度或短期编码便利被绕过。
- [ ] 代码排版清晰；没有为了少写几行而把多个逻辑动作合并成难以 Review 的单行实现。
- [ ] 新增和重命名的代码文件按业务职责命名，没有使用 `task1.ts`、`task2.ts`、`task3.ts` 等任务编号名称。
- [ ] 新增函数、全局变量、常量、宏定义或跨文件引用前已搜索现有实现，并已优先复用、扩展或重构；必要的新实现已有理由记录。
- [ ] 已确认代码可能出现问题的边界，并为异常输入、状态冲突、依赖失败、超时、资源限制和恢复路径补充保护或测试。
- [ ] 各函数对可能失败的操作有明确处理，不会静默忽略错误、默认放行或返回无法解释的结果。
- [ ] 默认使用 TypeScript，但语言/技术选择已根据实际场景评估；非 TypeScript 实现有明确的理由和边界记录。
- [ ] 已清理不再需要的函数、变量、业务逻辑、文件或目录；没有用注释掉的大段旧代码代替删除。
- [ ] 删除代码后已清理失效 import、导出、测试、脚本和文档，并通过 typecheck、build 和相关测试验证。
- [ ] 每个 Bug 或问题修复点附近都有“修改说明”备注，且备注注明实际修改日期（`YYYY-MM-DD`）和明确的修改原因。

- [ ] 相关测试已新增或更新，并且测试失败原因和通过结果可解释。
- [ ] 已完成 Code Review，并记录 findings、修复提交、回归测试和剩余风险。

- [ ] Task 完成提交、验收结果、Review 结果和合并到 `master` 的记录均已留存。
- [ ] 只有验收和 Review 成功后的 Task 分支才被合并到 `master`。
- [ ] 文档、注释、测试和实现没有互相矛盾。
