## 1. 文档目的

本矩阵将 PRD 中的产品目标、业务流程、功能、业务规则、质量约束和验收标准拆解为可设计、可开发、可测试、可追踪的软件需求。本文只描述系统必须提供的外部可观察行为和质量要求，不规定工作流框架、Agent 框架、数据库、接口协议、部署结构或其他技术实现。

## 2. 需求使用规则

### 2.1 规范性用语

- **必须**：V1 必须实现且验收时必须满足。
- **应**：V1 应实现；若受客观环境限制未满足，必须有经评审接受的偏差记录。
- **可**：允许实现的增强能力，不构成 V1 合格的必要条件。
- 每条原子需求使用唯一编号；需求发生实质变化时保留原编号并更新版本记录，不复用已废弃编号。

### 2.2 优先级

需求优先级沿用 PRD V1 的业务含义，不与发布门禁等级混用。发布门禁等级仅用于表达某条需求是否直接决定 V1 是否合格。

| 优先级 | PRD 原义 | 发布判定 |
| --- | --- | --- |
| P0 | 阻断性、最高紧急度；发生风险时优先通知并暂停相关流程 | 相关阻断要求必须满足；风险处置遵循 SR-WFL-018/019 |
| P1 | 本期必须完成的核心目标 | 原则上全部满足；偏差必须经过发布评审确认 |
| P2 | 重要但可根据风险和期限调整 | 应满足；偏差需记录影响和补救方案 |
| P3 | 低优先级优化，不得影响更高优先级事项 | 可延后，但不得阻塞、延迟或降低 P0/P1/P2 任务 |

### 2.3 状态

本文所有需求初始状态均为“候选基线”。完成产品、研发、测试三方评审后统一转为“已基线”；后续状态使用“已设计、开发中、待验证、已验证、已废弃”。

### 2.4 验收表达

“验收要点”描述最小可验证结果。详细测试用例应在测试设计阶段使用 `TC-<领域>-<序号>` 编号，并建立：

`PRD 条款 → SR 软件需求 → DS 设计项 → DEV 开发任务 → TC 测试用例 → DEF 缺陷 → EV 验收证据`

### 5.1 项目主状态

## 8. V1 保留的细化基线

以下内容虽然不是 PRD 中的原始数字或完整状态表，但 PRD 明确要求在需求矩阵阶段冻结，因此本矩阵保留并纳入 V1 正式验收范围。它们与 P0 硬性门禁的关系已经拆开：数据不丢失、审批不绕过、非法状态流转和追踪完整性属于硬门禁；性能时效、视口、样本规模和体验通过线属于正式验收目标。

1. 看板/视图状态 2 秒、通知 3 秒、本地交互 P95 2 秒、重启可见恢复 60 秒、1280×720 桌面视口的量化基线；桌面应用另以 AS-18 验收安装、启动、sidecar、升级和依赖降级。
2. 代表性项目 1 次完整端到端运行，以及 AS-02～AS-17 的最小异常/安全/恢复样本。
3. Boss 加至少 2 名非产品/研发背景体验者的理解性验收样本，以及“每人 6 项完成至少 5 项”的通过线。
4. V1 对周期、模型失败率、Token 和成本只建立透明基线，不用任一单项低成本或短耗时替代质量判定。
5. 项目、任务、通知状态机中由 PRD 推导出的新增流转继续保留，作为开发和测试共同遵守的 V1 候选业务规则。
6. 本矩阵冻结数据存储、备份恢复和保管的外部可验收约束；具体目录实现、Schema、接口、隔离和执行细节由概要设计与详细设计确定。
